# vender 调试与迁移验证计划

## 目标与边界

- 判断轻量控制层 + sing-box、daemon/TUI 分离的设计是否合理。
- 检查逻辑缺陷、实现 bug、权限与敏感信息保护、异常恢复能力。
- 实测 Ubuntu 到自建 VPS 和机场的数据面，不把端口可连接视为代理可用。
- 初步审查 Windows 11 迁移；Linux 交叉编译不能替代 Windows 实机验收。
- 本计划不含凭据、订阅 URL 或敏感配置原文；不提交交接文档。
- 当前阶段只阅读、只读采样、制定计划，不修改生产配置或服务。

## 已完成的初读与基线（2026-10-17）

- 已读交接文档、README、架构文档关键章节及配置渲染、DNS、状态、Windows 自启/系统代理关键源码。
- 本地仓库 HEAD：`a234b94`；开始检查时工作树干净。
- systemd 系统服务 active/running，以普通用户和网络 capabilities 运行，与交接拓扑一致。
- 安装的 vender 自报 `dev / commit none / built unknown`：尚不能证明与当前源码或发布包一致。
- CLI 状态显示 rule + TUN + manual（4 节点），但选中的是机场 Shadowsocks 节点，不是交接文档描述的 manual + auto。
- `cmd/vender/status.go` 主要读磁盘设置、检查 daemon 锁和 TCP 监听；不是实际数据面或内核当前出站的完整证明。

以上是观察，不预先认定 profile 跨组固定选择是 bug，也不认定现有代理已失效。

## P0：可恢复性与真实运行基线

1. 记录源码提交、已安装/运行中二进制路径、哈希、构建信息、sing-box 版本与特性；区分源码、发布包、部署三套产物。
2. 只读核对磁盘配置、daemon 控制通道、生成配置、Clash API 当前出站是否一致，解释上述 profile/节点偏差。
3. 记录主机 IPv4/IPv6、默认路由、策略路由、TUN、DNS、监听及已有代理/VPN；所有输出脱敏。
4. 为后续主动测试制作权限受限的配置备份和恢复脚本，规定每次变更的恢复验证；不依赖联网工具完成回滚。
5. 核实 agent 实际连接依赖，不能只凭 opencode.ai 直连规则就假定调试通道不会中断。

交付：可复核基线，以及生产主动测试的安全边界和恢复入口。

## P1：设计和源码审查

### 配置、订阅与控制面

- daemon 单一权威是否落实：CLI/TUI 写文件、控制命令、重启失败时是否出现磁盘/内存/内核状态分裂。
- 多文件保存的事务性、并发更新、失败回滚；profile 更新/删除/重名、跨 profile 固定选择、auto 空池及保留 tag 冲突。
- 链接/Clash 解析是否保留协议关键语义；不支持项是否明确拒绝，避免静默降级。
- 订阅请求的超时、大小限制、重定向、错误信息和日志脱敏；真实订阅请求仅访问已授权的供应商端点。
- 控制通道认证、文件权限、请求大小/超时、并发与流取消；Windows 下用 ACL 验证，不能照搬 POSIX 0600 的结论。

### DNS、路由与协议

- 路由与 DNS 优先级是否一致，尤其强制代理域名与 geosite-cn 重叠、用户规则、private/geoip 与 FakeIP 的组合。
- 节点入口解析与客户端解析隔离；机场 DNS 自身域名 bootstrap、TUN 下系统解析递归、缓存与切换后的污染。
- A/AAAA、HTTPS/SVCB/TXT、应用 DoH、SOCKS 本地/远端解析的行为与泄露边界。
- TUN 只有 IPv4 地址时的 IPv6 捕获范围；strict_route 不等同于通用 kill switch，须以实测定义行为。
- rule/global/direct 各模式的实际含义与文档一致性，critical-direct 不应被视为无条件全局保证。
- REALITY、Hy2、SS、VMess、Trojan 参数渲染和内核版本兼容；证书校验关闭与固定证书指纹的可行性。
- auto 的探测协议、误报、切换耗时、现有连接与新连接表现；同一 VPS 四入口不属于服务器级冗余。

### 进程与平台

- 启动就绪判定是否可能被其他监听进程误导；子进程意外退出、daemon 崩溃、锁与控制文件清理。
- restart/stop 并发、日志阻塞、流订阅泄漏、goroutine/data race、systemd 重启策略与权限传递。
- 把网络问题、供应商节点故障、内核问题、vender 问题分开归因。

交付：每项发现含严重度、文件/行号、触发条件、证据、影响、建议与待验证项。

## P2：隔离自动化验证

1. 在独立测试目录运行 `go test ./...`、`go vet ./...`、`go test -race ./...`，记录跳过项和环境依赖。
2. 检查现有测试是否只验证自身假设；为高风险状态转换和解析边界补充最小复现/回归用例。
3. 用固定版本真实 sing-box 检查渲染矩阵：三种模式 × 固定/auto × TUN 开关 × 有无 profile DNS，覆盖支持的协议。
4. Windows 交叉构建及测试编译；Windows API mock 通过仅算单元验证，不算系统功能通过。
5. 若需要新增测试或修复代码，单独记录变更；不自动替换生产二进制。

## P3：Ubuntu 端到端验证

先启动独立 config-dir/run-dir、独立端口、TUN 关闭的测试实例，不改变现有 daemon。

| 维度 | 验证内容 |
|---|---|
| 自建节点 | REALITY/Hy2 × IPv4/IPv6，分别固定测试；无 IPv6 时注明环境不具备条件 |
| 机场节点 | SS/VMess 各选代表节点；专属 DNS 正反对照；已知死节点不混作客户端失败 |
| 代理入口 | HTTP CONNECT、SOCKS5 远端解析、SOCKS5 本地解析；UDP 与 QUIC 在可控目标上验证 |
| 数据面 | TLS 校验有效的 HTTPS 请求、实际出口、下载完整性、有限大小吞吐与延迟/超时 |
| 路由 | 国内直连、海外代理、广告拒绝、LAN、本地服务、critical 与用户规则 |
| 故障恢复 | 隔离实例的坏节点、auto、内核退出、切换失败、DNS 超时；验证恢复结果 |

- 交叉对照：相同参数直接运行 sing-box，必要时只读检查 VPS 服务与日志；不修改远端服务。
- 外部请求设置超时、并发和流量上限，不默认遍历机场全部节点测速，不做无上限压测。
- 再安排生产 TUN 窗口：先备份/离线回滚就绪，再验证真实系统 DNS、TCP/UDP、IPv6、路由恢复与重启。
- 不在当前宿主机随意注入防火墙故障；断网/休眠/换网等破坏性场景优先隔离环境，必要时另行确认窗口。

交付：测试矩阵（通过/失败/环境受限/未测）、复现命令及脱敏证据。

## P4：Windows 11 初步迁移审查与实机清单

- 发布包依赖：确认该版本 sing-box 的 TUN 驱动需求，是否嵌入/需要额外 DLL，不直接采用交接文档推断。
- AppData/LocalAppData、中文/空格路径、原子替换、文件锁、ACL、管理员与普通用户访问同一控制端点。
- WinINET 系统代理与 WinHTTP/不遵循系统代理的应用区别；已有代理/PAC 是否备份恢复，异常退出是否残留。
- 计划任务的用户绑定、权限、失败重启、登录顺序、切换 TUN 后权限更新，以及中文 Windows 错误输出。
- Windows 子进程管理、daemon 被终止后的孤儿内核、驱动/路由/DNS 清理、防火墙和其他 VPN/WSL/Hyper-V 冲突。
- 真机按顺序验收：普通用户本地代理 → 系统代理 → 管理员 TUN → 登录自启 → 睡眠/唤醒/换网/重启 → 卸载恢复。

交付：迁移阻断项、待实机确认项及操作清单；没有 Win11 实机时明确不宣称迁移验证通过。

## 最终验收与修复顺序

- 优先处理失联/泄露/状态损坏/无法启动，其次错误分流与故障恢复，最后性能和界面。
- 每个确认 bug：最小复现 → 回归测试 → 最小修复 → 隔离验证；生产部署另设恢复点。
- 最终结论分别回答设计合理性、确认缺陷、Ubuntu 自建/机场可用性和 Win11 风险，不用单元测试通过代替端到端证据。
